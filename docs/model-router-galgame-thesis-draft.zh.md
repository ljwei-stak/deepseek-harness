# 面向大语言模型协作的质量约束成本感知路由方法

## 摘要

随着大语言模型服务从单一模型问答发展为多模型、多供应商和多模态协作，模型选择不再只是“能力越强越好”的排序问题。高性能模型通常具有更高的输入、输出和缓存费用；低价模型虽然适合批量和重复工作，却可能在复杂推理、长链路工程设计和高风险判断中产生质量损失。本文面向 DeepSeek Harness 的 Model Router + GALGame 插件，研究一种质量约束的成本感知多模型任务分配方法。该方法首先对用户请求进行任务类型识别、复杂度评估和依赖关系分析，然后将复杂请求拆分为问题建模、业务执行、验证审查和结果整合等工作包。系统以 LiveBench 的任务分类分数构造动态模型质量画像，以用户在设置页填写的输入、输出、缓存读取和缓存写入价格构造成本画像，并联合考虑专长、延迟、风险、关键度和模型多样性。对于每个工作包，算法先施加质量下限，再通过带重复路由惩罚的效用函数进行候选排序；当用户给出预算上限且初始方案超预算时，算法按工作包关键度从低到高进行可行的低价替换。最终输出包括任务拆分、模型指派、质量约束、费用估计、相对于全高质量基线的预计节省以及 LiveBench 数据新鲜度。

本文给出任务表示、模型画像、整数规划形式化、启发式求解算法、在线数据更新机制和实验设计。与仅使用单一高价模型或单一低价模型的方案相比，所提出方法的预期优势是：在满足质量下限的前提下减少高价模型调用，将高质量模型保留给高关键度和不可逆错误环节，并将可验证、重复和低关键度工作转移给低价模型。论文同时明确区分可审计的路由摘要与模型私有思维链，避免把内部推理过程作为产品输出。该研究可作为面向研究生阶段的多模型路由、组合优化和大模型系统工程课题。

**关键词：** 大语言模型；模型路由；混合专家；成本感知推理；任务分解；LiveBench；组合优化；多模型协作

## 1 研究背景与问题定义

### 1.1 背景

当前大语言模型生态同时存在多个能力层级和供应商接口。以代码工程任务为例，高水平模型适合架构设计、约束推理和最终审查，但其输出价格可能是轻量模型的数十倍；轻量模型适合生成样板代码、整理日志和执行格式转换，却不一定能可靠地完成架构决策。用户如果始终调用高价模型，质量通常较高但费用不可控；如果始终调用低价模型，费用较低却可能因为关键步骤错误而导致返工、风险积累和最终失败。

复杂请求通常不是一个不可分的“问答动作”，而是由多个具有不同业务属性的子任务组成。例如，“设计并实现一个带数据库、权限控制、测试和部署脚本的系统”至少包含：需求与约束提取、系统建模、接口与数据结构设计、代码生成、测试生成、风险审查和最终整合。这些子任务对模型能力的要求不同，理想方案不应把所有子任务绑定到同一个模型。

### 1.2 问题定义

给定用户请求 `x`、可用模型路由集合 `M`、任务分解得到的工作包集合 `I`，系统需要求解一个指派函数：

```text
assign: I -> M
```

使得：

1. 高关键度工作包的质量不低于相应质量下限；
2. 总费用尽可能低；
3. 不同业务方向尽量由擅长的模型处理；
4. 在预算可行时满足用户预算；
5. 延迟、风险和模型重复使用受到控制；
6. 数据不完整、LiveBench 暂时不可用或模型请求失败时仍能安全回退。

本文研究的不是训练新语言模型，而是模型选择、任务分配和在线决策。模型的能力是外部输入，路由器负责将能力、成本和任务需求组合成可解释、可复现的调用计划。

## 2 研究目标与贡献

本文拟实现以下目标：

1. 建立一个融合任务类型、复杂度、关键度、LiveBench 质量、价格、延迟、风险和专长的统一模型画像；
2. 建立带质量下限和可选预算约束的多工作包指派模型；
3. 设计适合桌面端实时运行的有界启发式求解器；
4. 通过 LiveBench 快照刷新和用户价格覆盖实现参数的在线更新；
5. 在用户界面提供任务分配、质量约束、费用和回退记录，而不泄漏模型私有思维链；
6. 设计对照、消融、敏感性和鲁棒性实验，验证质量—成本权衡；
7. 将算法实现、工程系统和论文模型保持一致，形成可复现的研究生级毕业设计。

相对于简单的全局模型排序，本文的主要贡献包括：

- 将“模型选择”提升为“工作包—模型指派”问题；
- 将质量下限作为约束，而不是仅作为效用函数中的软奖励；
- 将用户可校准价格与 LiveBench 的动态质量快照分离管理；
- 将模型重复使用惩罚和阶段关键度纳入分配；
- 设计预算超限时的低关键度替换机制；
- 在系统层面提供数据新鲜度、回退和估价的审计证据。

## 3 相关工作

### 3.1 Mixture-of-Models 与模型路由

Mixture-of-Models 的核心思想是由多个模型共同完成请求，而不是由单一模型承担全部计算。已有研究通常关注路由器如何根据输入难度选择不同模型，或者让多个模型以级联形式逐步升级。本文进一步将一个复杂请求拆成多个工作包，使不同模型可以在同一请求内分别承担建模、执行和验证职责。

### 3.2 LLM Cascade 与早停机制

LLM Cascade 常采用低成本模型先回答，只有在置信度不足时才调用高成本模型。该思路适合单一输出路径，但对工程任务的不同子环节不够细致。本文不是简单地先低后高，而是根据工作包关键度和质量下限直接确定可行候选，并在执行失败时进行显式路由回退。

### 3.3 成本感知推理

成本感知推理将 token 价格、延迟和质量放入同一个优化目标。本文特别保留输入、输出、缓存读取和缓存写入四类价格字段，允许用户在设置页按实际供应商和中转站价格校准，避免使用过时或不适用的公开价格。

### 3.4 LiveBench 与动态质量画像

LiveBench 是面向大模型能力比较的动态评测框架。实际部署中，排行榜接口格式、更新周期和模型名称可能变化，因此系统不将某个静态分数伪装为永远实时。本文采用“刷新快照—保留上次成功结果—回退实验基线”的数据生命周期，并保存数据来源和时间戳。

## 4 系统前提与建模假设

### 4.1 系统前提

系统假设 Harness 能够发现当前可用的 `(provider, model)` 路由，并能为一个请求指定 provider 和 model。不同 provider 可以对应官方 API、中转站、OpenCode Zen 或用户自定义兼容接口。模型目录只说明可用路由，不代表每次请求一定成功，因此算法必须允许执行阶段失败和回退。

### 4.2 建模假设

1. **可加费用假设。** 一次任务的总费用近似等于各工作包普通输入、缓存读写和输出费用之和；若没有可靠的缓存命中率，缓存读写比例取 0，避免虚构折扣。
2. **质量可比较假设。** LiveBench 分类分数、overall 分数和实验基线可以归一化到 `[0,1]`，从而参与同一评分函数。
3. **短期稳定假设。** 在一次任务执行期间，模型画像和价格不发生大幅变化；跨任务则允许通过 TTL 刷新。
4. **有限工作包假设。** 路由器生成的工作包数量较少，通常为 1 至 4 个，适合实时启发式求解。
5. **质量下限优先假设。** 对关键工作包，满足最低质量比少量节省费用更重要；只有在没有满足下限的候选时才允许约束放宽并记录。
6. **可验证性假设。** 测试、格式转换、摘要和代码样板等工作较容易通过规则或后续模型验证，因此适合低价模型。
7. **不输出私有思维链假设。** 系统只输出任务类别、特征、候选评分、指派结果和费用等可审计记录，不要求或展示模型隐式逐步思考。

## 5 任务表示与复杂度评估

### 5.1 任务类型

系统首先将请求映射到任务类型 `t`：

```text
t in {general, code, math, research, writing,
      vision, summarization, classification}
```

分类采用可解释的关键词和规则优先策略：图片、截图和识图请求归入 `vision`；证明、定理和公式请求归入 `math`；工程、代码、接口、部署和测试请求归入 `code`；论文、文献、引用和联网检索请求归入 `research`。规则分类的优点是确定性强、成本为零、可在离线时工作；缺点是对隐含意图的识别能力有限，后续实验可加入轻量分类模型。

### 5.2 复杂度特征

设请求文本为 `x`，定义：

- `l(x)`：按字符长度归一化的长度特征；
- `r(x)`：列表项、编号要求和显式约束数量；
- `d(x)`：代码、研究、数学、部署、视觉等领域标记数量；
- `c(x)`：代码/工程特征；
- `h(x)`：数学证明、研究、复杂、多步骤、评估等高推理特征；
- `v(x)`：图像和视觉特征。

当前实现使用以下可复现实例公式：

```text
l(x) = min(|x| / 2200, 1)
r(x) = min(number_of_requirements(x) / 8, 1)
d(x) = min(domain_markers(x) / 5, 1)

z(x) = 0.10 + 0.30 l(x) + 0.18 r(x) + 0.28 d(x)
       + 0.22 I_code(x) + 0.20 I_high_reasoning(x)
       + 0.12 I_vision(x)
```

复杂度 `D(x)=min(z(x),1)`，并划分为：

```text
simple    if D(x) < 0.34
balanced  if 0.34 <= D(x) < 0.66
complex   if D(x) >= 0.66
```

该公式不是语言模型生成的隐式判断，而是可单元测试、可解释和可调参的基线。实验阶段可以使用人工标注复杂度作为参照，计算准确率、宏平均 F1 和边界误差。

### 5.3 工作包与依赖图

对于简单和均衡请求，系统通常生成一个“直接回答与必要校验”工作包。对于复杂请求，系统先提取业务方向集合 `T(x)`，再为每个方向建立独立执行工作包；例如同时出现论文检索、数学证明、代码实现和截图分析时，执行图中会分别出现 `research`、`math`、`code` 和 `vision` 节点，而不是把它们压缩为一个总类别。复杂请求默认包含：

1. **问题建模与约束提取**：提取目标、约束、输入输出、验收标准和关键风险；
2. **业务方向处理**：为 `T(x)` 中每个方向执行代码、数学、研究、写作或视觉等核心工作；
3. **验证、反例与风险审查**：当原问题出现测试、验证、评估、对比或 audit 等要求时加入；
4. **结果校验与整合**：综合前置报告，形成面向用户的最终答案。

工作包构成一个有向无环图（DAG），后一阶段依赖前一阶段的结构化报告。阶段数不是固定常数，混合业务方向会增加执行节点，测试和评估要求会显式增加验证节点。各执行节点可以选择不同模型，从而把数学专长、代码专长和视觉专长分别纳入路由。

## 6 模型画像与数据来源

### 6.1 质量画像

对工作包 `i`、模型 `m` 和工作包业务类型 `t_i`，定义质量：

```text
Q(i,m) = LiveBench_category(m,t_i)
         or LiveBench_overall(m)
         or Q_baseline(m)
```

分数若以百分制返回则除以 100；若已经在 `[0,1]` 则直接使用。模型名称通过小写、去除标点和空格的规范化方法匹配，例如 `GPT 5.6 Sol` 与 `gpt-5.6-sol` 可以对应到同一行。

### 6.2 专长画像

模型目录为每个模型维护一个专长集合 `T_m`。若 `t in T_m`，则：

```text
S(m,t) = 1
```

通用任务使用 `0.58`，研究与写作之间存在可解释的迁移分数，其他不匹配情况使用 `0.38`。当 LiveBench 提供任务分类分数时，该分数优先用于专长匹配，从而使“专长”更多体现实时基准表现而不是固定标签。

### 6.3 价格画像

用户可为模型输入、输出、缓存读取和缓存写入填写价格：

```text
p(m) = (p_in(m), p_out(m), p_cache_read(m), p_cache_write(m))
```

用户价格优先于目录基线；如果同一模型通过不同中转站接入，则 `provider/model` 键优先于模型级键。未填写模型继续使用实验基线，但界面会明确显示“实验基线”。缓存价格不能在没有实际缓存 token 数的情况下直接乘到输入长度上，因此设置页另外记录缓存读取比例 `rho_r` 和缓存写入比例 `rho_w`，二者默认为 0，并限制在 `[0,1]`。对阶段 `i` 的输入 token 估计 `n_i^in`，定义：

```text
n_i^read  = floor(rho_r * n_i^in)
n_i^write = min(floor(rho_w * n_i^in), n_i^in - n_i^read)
n_i^bill  = n_i^in - n_i^read - n_i^write
```

只有用户确认供应商启用了 prompt cache 并填写比例时，缓存 token 才参与估价；否则全部输入按普通输入价格计费。这避免把“填写了缓存单价”误当成“本次请求一定命中缓存”。

### 6.4 延迟与风险

`L(m) in [0,1]` 表示归一化延迟，越小越快；`R(m) in [0,1]` 表示风险，包含模型质量不确定性、接口不稳定性和任务失配风险。工程部署中可以通过历史请求日志估计：

```text
L(m) = percentile_95(latency_m) / max_latency
R(m) = a * failure_rate_m + b * quality_variance_m
```

当前目录提供可运行的实验基线，后续可用在线反馈和实际请求数据校准。

## 7 数学优化模型

### 7.1 决策变量

令：

- `I`：工作包集合；
- `M`：可用模型集合；
- `t_i`：工作包 `i` 的业务类型；
- `x_im in {0,1}`：工作包 `i` 是否由模型 `m` 执行；
- `y_m in {0,1}`：模型 `m` 是否被本任务使用；
- `q_i`：工作包 `i` 的质量下限；
- `b`：用户预算上限；
- `k_i`：工作包关键度；
- `n_i^in, n_i^out`：输入和输出 token 估计。

### 7.2 基本约束

每个工作包必须且只能分配给一个模型：

```text
sum_m x_im = 1,  for every i in I
```

模型启用变量与指派变量关联：

```text
x_im <= y_m,  for every i,m
```

质量约束为：

```text
sum_m x_im Q(i,m) >= q_i,  for every i
```

若模型能力不足，候选集合为空，系统记录 `constraintRelaxed=true`，选择质量缺口最小的候选，而不是静默失败。

预算约束为：

```text
sum_i sum_m x_im Cost(i,m) <= b
```

当用户未设置预算或预算为零时，该约束不启用。对最终整合阶段可加入指定模型约束：

```text
x_i,deepseek-v4-pro = 1
```

但仅在该路由被发现且可用时启用，否则回退到可行候选。

### 7.3 多目标函数

定义缓存比例下的有效输入价格：

```text
p_eff_in(m) = (1-rho_r-rho_w) p_in(m)
               + rho_r p_cache_read(m) + rho_w p_cache_write(m)
```

再定义归一化成本收益：

```text
C(m) = 1 - ((p_eff_in(m) + p_out(m)) / 2) / p_max
```

其中 `p_max` 是当前候选和模型目录中的最大有效平均价格。延迟收益为 `1-L(m)`。对工作包 `i`、模型 `m` 的局部效用：

```text
U_im = w_q(c) Q(i,m) + w_c(c) C(m) + w_l(c) (1-L(m))
       + w_s(c) S(i,m) - w_r(c) R(m)
       - lambda d_m
       - kappa max(0, q_i-Q(i,m))
```

`d_m` 表示模型是否已服务其他工作包。重复使用惩罚鼓励业务方向分散，但不是硬性要求；当只有一个可用路由时，系统允许复用并在摘要中显示实际模型数量。

复杂度档位对应的权重为：

| 档位 | 质量 | 成本 | 延迟 | 专长 | 风险 |
|---|---:|---:|---:|---:|---:|
| simple | 0.30 | 0.50 | 0.14 | 0.04 | 0.02 |
| balanced | 0.45 | 0.30 | 0.10 | 0.10 | 0.05 |
| complex | 0.55 | 0.16 | 0.06 | 0.16 | 0.07 |

每行权重和为 1。简单问题强调成本和速度；复杂问题提高质量和专长影响。

### 7.4 质量下限

全局质量下限为：

```text
F_simple = 0.64
F_balanced = 0.72
F_complex = 0.78
```

复杂任务的工作包下限根据关键度调整：

```text
F_i = clamp(F_complex + 0.12 max(0, k_i - 0.65))
```

最终整合阶段至少使用 `0.84`。这使得算法不会为了极小的成本节省而把最终答复交给明显低于质量下限的模型。

### 7.5 成本模型

工作包费用估计为：

```text
n_i^bill = n_i^in - n_i^read - n_i^write
Cost(i,m) = (n_i^bill p_in(m) + n_i^read p_cache_read(m)
             + n_i^write p_cache_write(m) + n_i^out p_out(m)) / 10^6
```

其中 `n_i^read` 和 `n_i^write` 由第 6.3 节的比例给出。token 估计使用文本长度和阶段倍率：问题建模输入倍率为 `0.90`、输出倍率为 `0.55`；业务执行输入倍率为 `1.20`，复杂任务输出倍率为 `1.45`；验证输入倍率为 `1.15`、输出倍率为 `0.70`；整合输入倍率为 `1.65`、输出倍率为 `1.30`。估计值用于路由决策和用户提示，不等同于供应商最终账单；请求完成后若 provider 返回实际 usage，应使用实际 usage 覆盖估计值。

全高质量基线选择每个工作包中质量最高的候选，记为 `BaselineStrongCost`。预计节省率为：

```text
Saving = max(0, (BaselineStrongCost - TotalCost) / BaselineStrongCost)
```

## 8 求解算法

### 8.1 选择启发式

完整整数规划可以使用 MILP 求解器求得全局最优，但桌面端插件不宜引入重量级求解器，也不应因求解器启动失败阻塞问答。因此实现采用有界质量约束贪心算法：

1. 构建模型画像和工作包；
2. 按工作包顺序计算所有候选效用；
3. 过滤低于质量下限的候选；
4. 从未使用路由中选得分最高者；若为空则允许复用；
5. 最终阶段优先 DeepSeek V4 Pro；
6. 若总费用超过预算，从低关键度到高关键度尝试替换为更便宜的可行模型；
7. 重算总费用、节省率、使用模型数和约束状态。

### 8.2 伪代码

```text
ROUTE(request, available, prices, livebench, budget):
    complexity <- assess_complexity(request)
    task_type <- classify_task(request)
    packages <- decompose(request, task_type, complexity)
    profiles <- build_profiles(available, prices, livebench)
    used <- empty_set

    for package in packages:
        feasible <- [m in profiles |
                     quality(m, package) >= floor(package)]
        if feasible is empty:
            feasible <- profiles
            relaxed <- true
        candidate <- argmax_m utility(package, m, used)
        assign(package) <- candidate
        used.add(candidate.route)

    if synthesis_package exists:
        assign(synthesis_package) <- DeepSeek V4 Pro if feasible else fallback

    while total_cost(assign) > budget:
        package <- least_critical_movable_package()
        alternative <- cheapest_feasible_replacement(package)
        if alternative does not reduce cost: break
        assign(package) <- alternative

    return audit_record(assign, costs, constraints, livebench_status)
```

### 8.3 复杂度分析

设工作包数为 `|I|`，候选模型数为 `|M|`。候选效用计算为 `O(|I||M|)`，每个工作包排序为 `O(|M| log |M|)`，总复杂度为：

```text
O(|I||M| log |M|)
```

预算替换最多遍历 `|I|` 个非整合工作包和 `|M|` 个候选，仍保持同阶数量级。内存复杂度为 `O(|I|+|M|)`。在当前桌面端场景中，`|I|` 通常不超过 4，模型目录规模小于数百，实时计算开销可忽略。

### 8.4 最优性与局限

该启发式并不保证全局最优，特别是在共享上下文、缓存命中率和复杂依赖成本存在时。它的优点是确定、快速、易审计、无需外部求解器。实验中可将同一实例交给 MILP 求解器作为上界，计算启发式与最优解之间的最优性差距：

```text
gap = (heuristic_cost - optimal_cost) / optimal_cost
```

## 9 LiveBench 实时数据机制

### 9.1 数据适配

LiveBench 官网当前不是稳定 JSON API，而是由页面脚本发现最新 release，再加载 `table_YYYY_MM_DD.csv` 与 `categories_YYYY_MM_DD.json`。适配器默认访问官网根地址，解析 release 列表，将官方原始评测列按分类文件聚合为 reasoning、code、math、research、writing、summarization 等分数；同时接受 `models`、`data`、`leaderboard`、`results`、`entries` 等常见 JSON 数组封装，以及用户填写的 CSV 镜像。模型名经过规范化后匹配，百分制分数统一除以 100。官网资源路径或 schema 改变时，不会把 404 响应伪装为实时数据。

### 9.2 快照生命周期

每个 Agent 状态维护：

- `liveBench`：最近成功快照；
- `liveBenchFetchedAt`：获取时间；
- `liveBenchPromise`：请求去重；
- `liveBenchError`：最近一次错误。

若当前时间减去快照时间小于 TTL，则复用快照；否则发起带超时的请求。请求失败不阻塞对话：有旧快照时继续使用旧快照，没有旧快照时使用实验基线。UI 必须显示数据源和时间，不能把实验基线表述为实时 LiveBench。

### 9.3 数据质量控制

对每个分数进行有限性检查和 `[0,1]` 归一化；模型名使用稳定规范化；缺少某个任务分类时按 overall 回退。后续实验可加入：异常排名检测、分数漂移告警、快照签名、数据版本和人工批准机制。

## 10 用户价格手动校准机制

### 10.1 设计原因

用户可能使用中转站、OpenCode Zen 或供应商折扣，公开定价并不等于实际账单。将价格写死在代码中会导致路由优化方向错误，因此设置页允许用户逐模型维护价格，同时保留实验基线供首次使用。

### 10.2 数据结构

```json
{
  "pricing": {
    "qwen3.7-plus": {
      "input": 0.40,
      "output": 1.60,
      "cacheRead": 0.04,
      "cacheWrite": 0.50,
      "currency": "USD"
    }
  },
  "liveBenchEndpoint": "https://livebench.ai",
  "liveBenchTtlMs": 900000,
  "budgetUsd": 0,
  "cacheReadRatio": 0,
  "cacheWriteRatio": 0
}
```

价格单位固定为 USD/1M tokens。用户输入经过非负数 schema 校验，缓存比例经过 `[0,1]` 校验；保存时只写入模型路由设置命名空间，不触碰 LLM provider 的 API Key。设置变更会让已有计划失效，下一条任务重新计算。

### 10.3 校准实验

用户可以记录供应商账单中的真实 token 数和费用，计算校准误差：

```text
e_cost = |estimated_cost - billed_cost| / max(billed_cost, epsilon)
```

当某模型的系统性误差超过阈值，例如 10%，可更新价格或阶段 token 倍率。校准参数应按 provider/model 版本保存，并在实验中报告校准前后误差。

## 11 反馈学习与模型评分更新

用户对答案的赞、踩、修改、重试和继续追问可以形成反馈记录，但不能直接把一次主观评分等同于 LiveBench 客观质量。建议采用分层更新：

1. LiveBench 提供跨模型可比的外部质量先验；
2. 用户反馈形成任务域内的局部修正；
3. 实际失败率和延迟形成工程可靠性修正；
4. 只有达到最小样本量后才更新模型画像，避免单次异常主导路由。

可采用指数滑动更新：

```text
Q_hat_new(m,t) = (1-alpha) Q_hat_old(m,t) + alpha y
```

其中 `y` 是归一化反馈，`alpha` 随样本量递减。为了防止反馈投毒，应保留原始反馈、时间、任务类型和匿名会话标识，进行异常检测和权限控制。

## 12 实验设计

### 12.1 实验问题

本文建议验证以下研究问题：

- **RQ1：** 与全高价模型相比，算法能否在质量不显著下降的情况下减少费用？
- **RQ2：** 与全低价模型相比，任务拆分和质量下限能否提升复杂任务质量？
- **RQ3：** LiveBench 任务分类分数是否优于单一 overall 分数？
- **RQ4：** 专长权重、质量下限和预算修复分别贡献多少？
- **RQ5：** LiveBench 暂时不可用或价格发生偏差时，系统是否稳定回退？

### 12.2 任务集

建议构建 200 至 500 条任务，覆盖：

| 类别 | 示例 | 关键指标 |
|---|---|---|
| 简单问答 | 概念解释、短翻译、格式转换 | 正确率、延迟、成本 |
| 代码 | API、数据库、测试和部署 | 编译率、测试通过率、漏洞数 |
| 数学 | 定理证明、公式推导、数值计算 | 结论正确率、证明完整性 |
| 研究 | 文献综述、联网核验、引用整理 | 引用准确率、事实一致性 |
| 写作 | 报告、开题、技术文档 | 人工评分、结构完整性 |
| 视觉 | 截图理解、图表解释、文档识别 | 识别准确率、幻觉率 |
| 复杂工程 | 多模块系统设计与实现 | 端到端验收率、返工次数 |

每条复杂任务由至少两名具有软件或研究经验的标注者标注工作包、关键度和质量下限。标注分歧通过第三名标注者或讨论解决，并报告 Cohen's kappa 或 Krippendorff's alpha。

### 12.3 对照组

1. **All-Strong**：所有工作包都使用质量最高的高价模型；
2. **All-Cheap**：所有工作包都使用最低价模型；
3. **Global-Best**：为整个请求选择一个全局综合分最高模型；
4. **Cascade**：低价模型先答，置信度不足时升级；
5. **Router-Full**：本文完整算法，包含 LiveBench 分类分数、专长、质量下限、预算和多样性惩罚；
6. **Router-NoLiveBench**：使用固定实验质量；
7. **Router-NoFloor**：移除质量下限；
8. **Router-NoSpecialty**：移除任务专长项。

### 12.4 评价指标

- **任务成功率：** 是否满足预先定义的验收条件；
- **质量得分：** 由盲评专家或任务专用自动评测器给出；
- **总费用：** 供应商真实账单或按统一价格重算；
- **节省率：** 相对 All-Strong 的费用减少比例；
- **质量约束违约率：** `Q(i,m)<F(i)` 的工作包比例；
- **端到端延迟：** 从请求提交到最终答案完成的时间；
- **模型多样性：** 一个任务实际使用的 distinct routes 数；
- **返工率：** 用户因关键错误要求重做的比例；
- **估价误差：** 估计费用与账单费用的相对误差；
- **回退成功率：** 首选模型失败后最终成功完成的比例。

### 12.5 统计方法

每条任务在不同方法下使用相同输入、相同附件和相同随机种子（如接口支持）。对于质量和成功率，使用配对 bootstrap 置信区间；对于费用和延迟，报告中位数、四分位距和 95% 置信区间。多组比较可使用 Friedman 检验和 Nemenyi 事后检验；两组配对比较可使用 Wilcoxon 符号秩检验。除 p 值外，必须报告效应量和实际费用差异。

## 13 消融实验与敏感性分析

### 13.1 消融项

1. 移除质量下限：观察高价模型是否被过度替换，以及质量约束违约率变化；
2. 移除专长权重：观察跨业务方向误分配；
3. 移除成本项：结果应接近 All-Strong；
4. 移除多样性惩罚：观察是否所有工作包都集中到一个模型；
5. 移除 LiveBench 动态更新：观察模型版本变化后的质量下降；
6. 移除预算修复：观察预算超限率；
7. 移除用户价格覆盖：比较公开基线与真实中转站价格下的选择差异。

### 13.2 参数敏感性

对质量权重、质量下限、重复惩罚 `lambda`、质量缺口惩罚 `kappa` 和 TTL 做网格实验。重点观察：

- 质量权重提高是否导致费用单调上升；
- 质量下限从 0.70 增至 0.90 时成功率和节省率的拐点；
- 过大的多样性惩罚是否迫使任务使用不合适的模型；
- TTL 过短是否增加网络开销，过长是否造成陈旧画像；
- token 倍率误差对模型排序的敏感性。

可使用 Pareto 前沿展示“质量—费用—延迟”三目标关系，而不是只报告一个加权分。

## 14 模型调整与在线迭代

### 14.1 初始参数

初始权重依据任务风险直觉设定：简单请求成本权重为 0.50，复杂请求质量权重为 0.55、专长权重为 0.16。初始质量下限取 0.64、0.72 和 0.78，最终整合取 0.84。所有初值必须在实验中重新估计，不能把经验参数当作普适常数。

### 14.2 离线调参

在训练集上使用网格搜索、贝叶斯优化或坐标下降最小化：

```text
J(theta) = a * quality_loss(theta)
           + b * normalized_cost(theta)
           + c * latency_loss(theta)
           + d * constraint_violation(theta)
```

验证集用于选择 `theta`，测试集只在最终报告中使用。按任务类型分层调参，防止代码任务的最优权重覆盖数学或视觉任务。

### 14.3 在线校准

线上每个任务产生一条审计记录，包含输入特征、候选分数、实际路由、估计费用、真实延迟、错误和用户反馈。系统按时间窗口重新计算价格和可靠性统计；只有超过最小样本量、置信区间足够窄时才更新模型画像。LiveBench 外部质量和用户反馈分开存储，并在路由摘要中分别标记来源。

## 15 工程实现

### 15.1 Host 侧

Host 插件入口为 `.dsh-plugin/index.mjs`，负责：

- 发现可用 provider/model；
- 注册 `model-router` 设置命名空间；
- 读取用户价格、LiveBench 地址、TTL 和预算；
- 调用 `buildPlan` 生成计划；
- 在 `agent/request` 阶段覆盖当前工作阶段的 provider/model；
- 在 `agent/turn-stopping` 阶段注入下一阶段；
- 在模型不可用时记录失败并执行回退。

### 15.2 共享算法

`.dsh-plugin/shared/router.mjs` 保存复杂度评估、任务分类、模型目录、费用估计和指派算法；`.dsh-plugin/shared/livebench.mjs` 负责排行榜 schema 适配和快照获取。Host 与 GAL 客户端共享同一份计划结构，避免界面显示与实际调用不一致。

### 15.3 客户端

客户端在 `SettingsTab.jsx` 提供价格和预算编辑器，在 `GalPanels.jsx` 展示质量下限、阶段 token、阶段费用、LiveBench 时间戳和节省率。`GalView` 继续使用现有存档、附件、MarkdownText 和 KaTeX 能力。独立客户端 bundle 通过 `scripts/build-client.mjs` 生成，构建时注入 Markdown 样式并保留 React 兼容桥接。

### 15.4 数据一致性

设置保存使用 Host settings API 的 namespace revision，避免两个页面并发覆盖。价格修改会使当前路由计划失效；单独会话不读取集体计划。LiveBench 请求进行去重和超时控制，失败不会导致主对话失败。

## 16 可解释性、安全与隐私

### 16.1 可解释性

界面展示：任务类型、复杂度、权重、质量下限、候选分数、实际指派、阶段 token、阶段费用、LiveBench 来源、预算状态和回退记录。这些内容足以审计“为什么选择某模型”和“预计花费多少”，但不冒充模型内部思维链。

### 16.2 密钥与价格隔离

价格设置命名空间不保存 API Key。API Key 继续由 Harness 原生凭据和 provider 设置管理。LiveBench endpoint 是用户可编辑的网络目标，应限制请求方法、设置超时并避免把敏感请求内容发送到排行榜接口。

### 16.3 不可信数据

LiveBench 返回内容、用户反馈和模型输出都属于不可信数据。解析器只读取允许的数字和字符串字段；反馈不能直接执行为路由代码；模型输出中的 Markdown 和附件必须经过现有渲染及大小限制。联网失败、模型 404/429/区域限制等错误应转为可见回退记录。

## 17 误差来源与局限

1. LiveBench 评分不等于特定用户任务的真实质量；
2. 关键词复杂度可能误判隐含难度；
3. token 长度估计和阶段倍率无法完全预测实际输出；
4. 公开价格和中转站账单可能存在折扣、缓存和汇率差异；
5. 贪心算法不保证全局最优；
6. 多模型串行调用会增加上下文传递和端到端延迟；
7. 低价模型生成的代码即使通过格式检查，也可能包含语义缺陷；
8. 用户反馈存在主观性和选择偏差；
9. LiveBench endpoint schema 变化可能造成字段缺失；
10. 缓存比例目前由用户显式填写，尚未从各供应商实际 usage 自动学习命中概率；正式部署应以 provider 返回的 cache read/write token 覆盖估计值。

这些局限并不意味着算法不可用，而是说明实验报告必须同时给出质量、成本、延迟和失败率，不能只展示节省金额。

## 18 预期结果与讨论框架

如果假设成立，Router-Full 应呈现以下趋势：

- 对简单任务接近 All-Cheap 的费用和延迟，但质量不低于设定下限；
- 对复杂工程任务显著优于 All-Cheap 的成功率，同时比 All-Strong 少调用高价模型；
- 相比 Global-Best，业务方向拆分带来更高的模型多样性和更低的返工率；
- 移除质量下限后费用下降但约束违约率和关键错误上升；
- 移除 LiveBench 分类后，视觉、数学和代码任务出现更明显的错配；
- 用户价格校准后，路由选择随实际供应商价格变化，估价误差下降。

若实验未出现这些趋势，应优先检查任务标注、LiveBench 映射、价格单位、token 倍率和候选发现是否正确，而不是直接增加高价模型权重。

## 19 结论与未来工作

本文为多模型协作系统建立了一个质量约束、成本感知、可解释且可在线更新的路由框架。核心思想是把复杂任务拆成具有不同关键度和业务方向的工作包，在质量下限保护下，将高价模型用于不可替代的建模、审查和整合环节，将低价模型用于大量、重复和可验证工作。LiveBench 提供动态质量先验，用户设置提供真实价格，二者通过快照和覆盖层解耦；预算修复和失败回退使方案适合桌面端真实运行。

后续工作包括：

1. 引入 MILP 或 CP-SAT 作为离线最优性基准；
2. 使用实际请求日志学习延迟、失败率和任务专长；
3. 将缓存命中率、并行执行和上下文传输成本纳入完整账单模型；
4. 使用轻量语义分类器改进隐含任务识别；
5. 将工作包依赖图扩展为可并行 DAG，优化端到端延迟；
6. 引入基于置信区间的安全探索，避免在线反馈导致模型画像漂移；
7. 建立版本化 LiveBench 数据集和可复现实验流水线；
8. 研究多模态任务中图像分辨率、OCR 成本和视觉质量的联合优化。
